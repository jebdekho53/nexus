# Matrix product direction

User-confirmed direction, 25 October 2026.

- Matrix is the user's own independent software. TS/Brahmos is a competitor and a functional benchmark.
- Aim for comparable user-facing capabilities and booking reliability through Matrix's maintained implementation. Supplied extracted competitor artifacts are reference evidence; do not confuse recovered pseudocode with validated behavior.
- Preserve Matrix's General GN Book Now capability outside the scheduled 08:00, 10:00 and 11:00 opening modes. Scheduled and ordinary booking must remain separate.
- Immediate priorities: Chromium behavior, 08:00 opening timing and high-load recovery, verified through the actual active runtime and booking request chain.
- Avoid copying competitor branding or adding complex V8 packaging, vendor-server dependencies or licensing architecture merely to imitate its protection mechanisms. Matrix's own security needs are separate from booking feature parity.
- Optimize collaboration for limited usage: reuse existing reports and evidence, perform focused inspection, use narrow meaningful tests during iteration, and run full suites at integration/release checkpoints. Avoid repeated broad scans, duplicate builds and unnecessary parallel agents.
- Validate real default adapters, form shapes and request construction, not only isolated helpers with hand-wired dependencies.
- Report source implementation, synthetic tests, packaged startup and live login-to-QR evidence separately. Passing offline tests is not proof of successful live booking or a guarantee of next-day performance.
- The practical goal is successful Matrix bookings with behavior comparable to the competitor. Preserve payment safety and original journey details; do not make unverified success claims.

Read this note when continuing feature-parity or reliability work. See release and backend-comparison reports for technical evidence and outstanding live-validation limits.
